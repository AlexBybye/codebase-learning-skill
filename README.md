# Code Analyzer v2.1：从移动端分析器到全栈 + AI 仓库学习器

## 1. 先说结论

Code Analyzer v2.1 已覆盖当前项目运行时。它从移动端专项分析器扩展为 Web、Mobile、Backend、Data/Infra、AI 五域仓库学习器；当前 `.claude-plugin/`、`agents/`、`skills/` 共 8 个运行时文件。各领域先完成取证，再由共享解释层组织成更容易理解的学习地图；机器合同和证据字段保持原样。

## 2. 这次真正变了什么

| 维度     | 旧版                                               | v2.1                                                  | 结果                                 |
| -------- | -------------------------------------------------- | ----------------------------------------------------- | ------------------------------------ |
| 产品定位 | 移动端模块分析器                                   | Web、Mobile、Backend、Data/Infra、AI 与混合仓库学习器 | 顶层域从 1 个增至 5 个               |
| 编排方式 | 固定三阶段串行流水线，详情阶段固定调用四个子 Skill | 浅层发现、五域路由、仅加载 relevant 域合同            | 空域不再启动专项分析                 |
| 单元模型 | 固定 Page/API/Card/Feature 分类                    | 从真实入口建立少量业务流单元                          | 适配非 UI 与跨域仓库                 |
| 证据合同 | 仅部分模板有完整字段级证据                         | 所有关键事实和调用边统一 `source/evidence`            | 直接事实、配置、推断、缺失边界可区分 |
| 解释方式 | 各领域模板各自组织输出                             | 共享忠实解释层统一“作用→入口→流转→边界→证据”          | 更易读且不改机器合同                 |
| 跨域链路 | 不是一级合同                                       | 混合仓库至少输出一条逐跳有证据的端到端路径            | UI/API/Data/AI 可闭环解释            |
| 恢复方式 | Stage/分类状态，详情偏追加                         | 稳定 unit ID、产物/章节/证据锚点、整体重建            | 降低重复章节与全量重跑风险           |
| 项目耦合 | 含组织专用默认值和移动端假设                       | 专有名称只能从目标源码发现                            | 已知专有标识从 30 降至 0             |

## 4. 它现在怎么工作

### 旧版

```text
入口 Agent
  → 全仓扫描与移动分层
  → 固定 Page/API/Card/Feature 划分
  → 固定 Detail 编排
      → API Detail
      → Card Detail
      → Page Detail
      → Feature Detail
```

旧版严格串行执行三个阶段，四个详情分支按固定顺序进入任务，即使某一类为空也不会提前退出。大仓模式只调整分批或优先顺序，不会从后续流程中裁掉无关领域。

### v2.1

```text
薄入口 Adapter
  → 一次浅层文件/配置发现
  → 深入前写五域 route-plan
  → 只加载 relevant 域 reference
  → 按真实入口建立有界业务流 unit
  → 共享证据台账并连接跨域路径
  → 忠实解释层统一作用、入口、流转、边界和证据
  → 排序后整体重建学习地图
```

v2.1 只调用一个主 Skill，再根据证据加载 `R` 个领域参考文件，其中 `0 <= R <= 5`。标为 `skipped` 的领域不会运行专项合同，也不会生成空模板。

## 6. 五个领域能解释到什么程度

五个领域都遵守同一组 6 项核心解释门槛：

1. 真实入口或注册关系；
2. 有界业务流单元；
3. 数据与控制流追踪；
4. 外部或缺失边界；
5. 状态、结果、错误或降级；
6. 字段级 `source/evidence`。

| 域         | 入口与结构                                                 | 调用链与边界                                                                       | 明确输出类别 | 核心门槛 |
| ---------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------- | -----------: | -------: |
| Web        | 浏览器挂载、路由、页面、关键组件、状态、loader/action      | 用户或生命周期事件到请求、响应映射、渲染/导航、空态/错误                           |            5 |      6/6 |
| Mobile     | App target、页面/组件、导航、状态及可选数据层              | 生命周期/事件到状态、客户端/本地存储、UI 消费                                      |            6 |      6/6 |
| Backend    | HTTP/RPC/GraphQL、事件、worker/job、schedule、queue、CLI   | middleware/鉴权/校验到 service、持久化、集成、response/ack/retry/fallback          |            5 |      6/6 |
| Data/Infra | persistence、cache、messaging、build/deploy、observability | schema/migration/transaction、缓存回源/失效、消息收发/确认、部署声明和遥测         |            5 |      6/6 |
| AI         | 被真实入口使用的 AI 实现与十阶段流水线                     | ingestion、retrieval、prompt/model、tools、结构化输出/引用、评测、安全、成本和降级 |            6 |      6/6 |

这里所说的“与 Mobile 等价”，是指五个领域都能把入口、业务流、边界和源码证据连起来，并不表示每个专项都已经穷尽。当前仍缺统一的相关测试解释；异步取消、消息顺序与背压、隔离与锁、streaming/session cancellation 等高级并发语义仍属于 P1 深挖项。

### 统一解释层

领域合同负责“查什么、追什么”，共享层负责“怎样让人读懂”。每个单元先交代作用，再解释入口、真实流转、结果和缺失边界，最后给出证据。项目术语首次出现时保留原名，并补充简短说明。

该层不得改写标识符、路径、配置键、代码、精确 JSON、状态、章节锚点、数字、条件、不确定性或 `source/evidence`。类比只能辅助理解，不能充当证据。

### 移动端保留与取舍

v2.1 保留页面/组件、布局、状态、导航、生命周期、客户端出站调用、本地存储/cache、错误/空态和源码可证视觉字段。

旧版用更刚性的逐项模板描述布局、字体、颜色、图标和 API 请求/响应字段。v2.1 改为领域合同，不再强制所有仓库使用同一种版式，以此换取跨栈覆盖和更小上下文。如果任务需要像素级 UI 资产盘点或固定 API 文档格式，旧版模板仍然更严格。

## 7. 结论如何回到源码

每条关键路由理由、结论、调用边和缺失环节必须同时写出：

- `source: code`：由当前源码具体符号直接证明；
- `source: config`：由仓库管理的配置、schema、migration、构建或部署键直接证明；
- `source: inferred`：至少两个独立锚点支持，并写明推断过程；
- `source: unavailable`：当前边界无法闭合，并说明检查范围和缺失连接。

证据只能使用相对目标根目录的 `path#symbol`、`path#key` 或行号锚点。绝对用户路径、旧分析文档和仅有依赖名称不能代替实现证据。项目品牌、客户端、协议、模型、设计系统和基础设施名称只能在目标源码或配置真实出现时写入产物。

## 8. 续跑、恢复与幂等

| 行为           | 旧版                                     | v2.1                                                |
| -------------- | ---------------------------------------- | --------------------------------------------------- |
| 恢复键         | Stage/分类状态                           | 稳定业务流 unit ID                                  |
| completed 定位 | 隐含在分类产物中                         | artifact、section anchors、evidence anchors         |
| 重试写入       | 在详情文件末尾追加                       | 替换单个 unit 区块后排序整体重写                    |
| 旧状态歧义     | 可能再次追加                             | 零/多命中标记 `state_inconsistent`，不复制可疑内容 |
| 失败隔离       | 任一 Stage 失败即停止整条流水线          | 不依赖失败单元的其他 unit 可继续                    |
| 确定性         | append、timestamp 和遍历顺序可能影响结果 | 禁止时间/随机 ID；每个稳定 ID 仅一个区块            |

尚未运行真实的二次重试来验证字节一致性，因此本节只能证明指令合同，不能证明实际运行结果。

## 9. 读写与运行边界

v2.1 只读取用户选定的目标仓库，并且只允许在解析、校验后的 `doc/analysis/` 下写入分析产物。它不得修改业务代码；默认不运行应用、测试、构建或 migration，不安装依赖，不读取凭据，不联网或调用外部服务，也不清理分析目录中的无关文件。

这些约束属于指令合同，不是操作系统级沙箱。入口仍然拥有通用读写工具，因此目前不能声称已经具备机械路径隔离。
